# Delivery Insight 발표 스크립트 초안

- 기준 자료: `delivery-insight-course-presentation.pptx.pdf` 19장
- 예상 발표 시간: 약 14분 10초 + 화면 전환과 호흡
- 핵심 강조: 7~10장 추천 기능, 특히 상태공간 다익스트라

## 1. 표지 - 0:25

안녕하세요. 1팀의 배송 관리 서비스, Delivery Insight를 발표하겠습니다.

저희 서비스는 배송 계획을 단순히 저장하는 데서 끝나지 않고, 오늘의 배송 현황과 기상 위험을 함께 보고 기사에게 더 안전한 다음 배송지를 추천하는 서비스입니다.

발표에서는 전체 서비스 흐름을 먼저 보여드리고, 실제 웹 기능에 적용한 상태공간 다익스트라를 중심으로 설명드리겠습니다.

## 2. 문제 정의 - 0:45

저희가 시작한 질문은 단순했습니다. 비 오는 날에는 어느 집부터 가야 할까?

기존 배송 순서는 주로 거리나 기사 경험에 의존합니다. 하지만 가까운 곳이라도 폭우나 폭염 같은 위험이 있다면 먼저 방문하는 것이 항상 좋은 선택은 아닙니다.

또 관리자는 오늘의 물량과 위험 배송지를 한눈에 보기 어렵고, 날씨 API 같은 외부 서비스가 실패했을 때 배송 계획 저장까지 실패할 수 있다는 문제도 있었습니다.

그래서 관리 화면, 기상 위험도, 안전 우선 추천을 하나의 업무 흐름으로 묶었습니다.

## 3. 관리자와 기사 화면 - 0:35

서비스의 사용자는 관리자와 배송 기사입니다.

관리자는 기사별 배송 계획을 만들고, 현재와 미래, 완료 계획을 나눠 보면서 오늘 위험한 배송지가 어디인지 확인합니다.

기사는 자신에게 할당된 계획 안에서 배송 상태와 위험도를 확인하고, 서비스가 제안하는 다음 행동을 선택합니다.

즉 관리자의 운영 판단이 기사의 실제 실행으로 이어지는 구조입니다.

## 4. 사용자 흐름 - 0:35

전체 흐름은 다섯 단계입니다.

관리자가 배송 계획을 할당하면 배송지별 날씨를 바탕으로 위험도를 계산합니다. 기사가 배송을 시작하면 다음 배송지를 추천하고, 배송 완료 결과는 남은 집과 박스 수에 반영됩니다.

이 중 핵심은 네 번째 단계입니다. 가장 가까운 집을 바로 선택하는 것이 아니라, 먼저 안전한 후보를 고르고 그 안에서 전체 이동 효율이 좋은 순서를 찾습니다.

## 5. 운영 대시보드 - 0:45

메인 화면에서는 오늘 배송할 집, 완료된 집, 전체 박스와 배송된 박스를 한 번에 보여줍니다.

단순 건수뿐 아니라 진행률을 함께 표시해서 관리자가 지금 배송이 얼마나 진행됐는지 바로 판단할 수 있게 했습니다.

아래에는 진행 중인 계획, 출발 대기 계획, 위험 배송지 수를 분리했습니다. 미래 계획의 수치까지 섞기보다 오늘 실제 행동에 필요한 정보에 집중했습니다.

## 6. 아키텍처 - 0:45

구조는 React SPA와 Spring Boot 단일 애플리케이션으로 구성했습니다.

팀 규모와 로컬 데모 환경을 고려해 마이크로서비스로 나누기보다, 하나의 배포 단위 안에서 API, 서비스, 이벤트, 스케줄러, 도메인과 저장소의 책임을 분리했습니다.

MySQL은 배송 업무 데이터를, Redis는 Refresh Token의 유효 상태를 관리합니다. 카카오 API는 주소 좌표와 경로 시간을 제공하고, 기상 API 데이터는 배송지 위험도 계산에 사용합니다.

## 7. 추천 결과의 제품 연결 - 0:40

여기부터가 저희가 가장 강조하고 싶은 추천 기능입니다.

[지도와 추천 카드를 가리키며]

계산 결과는 백엔드 숫자로만 끝나지 않습니다. 지도에서 파란 마커로 다음 배송지를 강조하고, 추천 카드에는 주소, 안전 등급, 위험 점수와 카카오 도로 기준 예상 시간을 보여줍니다.

즉 알고리즘의 출력이 기사가 바로 다음 행동을 고를 수 있는 UI로 연결됩니다.

## 8. 배송 완료 후 재계산 - 0:35

추천은 한 번 계산하고 끝나는 정적인 경로가 아닙니다.

배송지 하나를 완료하면 가장 최근 완료 지점이 새로운 현재 위치가 됩니다. 아직 완료되지 않은 배송지 중 앞으로 최대 다섯 곳을 다시 후보로 만들고, 위험도와 이동 순서를 다시 계산합니다.

그래서 배송 진행 상황이 바뀔 때마다 현재 위치에 맞는 다음 추천이 새로 만들어집니다.

## 9. 상태공간 다익스트라 - 1:15

여기서 일반 다익스트라와 저희 구현의 차이가 생깁니다.

일반 다익스트라는 보통 현재 정점 하나를 상태로 보고, 출발점에서 특정 목적지까지의 최단거리를 구합니다.

하지만 배송 순서에서는 현재 위치만으로 상태를 설명할 수 없습니다. 똑같이 A 배송지에 있더라도 B와 C를 이미 방문한 경우와, 아직 방문하지 않은 경우에는 앞으로 해야 할 일이 완전히 다릅니다.

그래서 저희는 상태를 `현재 위치`와 `이미 방문한 배송지 집합`의 조합으로 정의했습니다. 예를 들면 `(A, {B, C})`가 하나의 상태가 됩니다.

이 상태에서 아직 방문하지 않은 배송지로 이동할 때마다 새로운 상태와 누적 비용이 만들어집니다. 우선순위 큐에서는 누적 이동시간이 가장 작은 상태부터 꺼내고, 같은 상태에 더 큰 비용으로 도착한 경로는 제거합니다.

모든 후보를 방문한 상태가 큐에서 처음 나오는 순간, 그 경로가 전체 누적 이동시간이 가장 작은 순서가 됩니다.

한 문장으로 정리하면, 저희 그래프의 정점은 배송지 하나가 아니라 `현재 위치와 방문 집합의 조합`입니다.

## 10. 알고리즘 흐름과 트레이드오프 - 1:20

실제 추천 흐름은 다섯 단계입니다.

먼저 미완료 배송지를 최대 다섯 곳으로 제한합니다. 그다음 위험 등급과 위험 점수의 우선순위가 가장 낮은, 즉 가장 안전한 후보만 남깁니다.

선택된 후보 사이에는 위도와 경도의 Haversine 직선거리를 초 단위 비용으로 바꾼 행렬을 만들고, 방금 설명한 상태공간 다익스트라로 전체 방문 순서를 계산합니다. 완성된 순서의 첫 번째 배송지가 지금 기사에게 보여줄 다음 추천입니다.

가장 어려웠던 점은 세 가지였습니다.

첫째, 방문 집합이 들어가면 상태 수가 대략 `N 곱하기 2의 N승`으로 증가합니다. 그래서 서비스에서는 후보를 최대 다섯 곳으로 제한했습니다.

둘째, 매 순간 가장 가까운 곳을 고르는 탐욕 방식은 전체 최적을 보장하지 않습니다. 단위 테스트에서도 첫 구간만 보면 1초인 경로가 이후 100초 구간으로 이어지는 반면, 처음에 2초 거리의 다른 지점을 선택하면 전체를 4초에 방문하도록 비용 행렬을 구성해 차이를 검증했습니다.

셋째, 모든 후보 쌍에 카카오 API를 호출하면 지연과 호출량이 커집니다. 그래서 전체 순서 계산에는 가상 비용을 사용하고, 최종 추천된 첫 구간만 카카오 길찾기 예상 시간으로 보완했습니다.

## 11. Refresh Token 개선 - 0:50

다음은 인증에서 해결한 문제입니다.

처음에는 Refresh Token을 HttpOnly Cookie로 전달하고 JWT 서명과 만료만 검증했습니다. 이 방식은 서버가 현재 어떤 Refresh Token을 허용하고 있는지 직접 제어하기 어렵습니다.

개선 후에는 Cookie가 토큰 전달을 담당하고, Redis가 토큰의 유효 상태를 관리하도록 역할을 나눴습니다.

재발급 요청이 오면 JWT 자체를 검증한 뒤 Redis에 저장된 값과 비교하고, 일치할 때만 Access Token과 새로운 Refresh Token을 발급합니다.

## 12. Redis를 선택한 이유 - 0:45

Redis를 사용하면서 얻은 효과는 세 가지입니다.

첫째, Refresh Token 만료시간과 Redis TTL을 동일하게 설정해 별도 정리 작업 없이 자동으로 삭제되게 했습니다.

둘째, 로그아웃할 때 브라우저 Cookie만 없애는 것이 아니라 Redis의 토큰도 삭제해 서버 로그아웃을 구현했습니다.

셋째, Refresh Token을 회전시켜 이전 토큰이 다시 사용되는 것을 차단할 수 있게 했습니다.

여기서 Redis는 단순 캐시라기보다, 서버가 현재 허용한 Refresh Token의 상태 저장소 역할을 합니다.

## 13. 탈취 토큰 재사용 차단 - 0:50

이 흐름을 토큰 탈취 상황으로 보면 더 명확합니다.

공격자가 예전 Refresh Token으로 재발급을 요청하더라도 JWT 서명과 만료 검증 뒤에 Redis 값 비교가 한 번 더 수행됩니다.

사용자가 로그아웃했거나 정상 재발급 과정에서 토큰이 회전됐다면 Redis에는 이미 새로운 값이 저장되어 있으므로, 탈취된 이전 토큰은 일치하지 않아 거부됩니다.

물론 Redis가 탈취 자체를 막는 것은 아닙니다. 대신 탈취 이후 서버에서 토큰을 폐기하고 재사용 가능 시간을 줄일 수 있다는 점이 핵심입니다.

## 14. N+1과 고정 쿼리 - 0:50

배송 상세는 배송지, 상품, 위험도와 위험요인처럼 여러 연관 데이터를 가집니다. 이를 객체 그래프를 따라 단순 조회하면 배송지가 늘어날 때 N+1 문제가 발생할 수 있습니다.

목록 화면은 필요한 집계 값을 Native SQL Projection 한 번으로 조회했습니다. 상세 화면은 계획과 배송지, 상품, 위험요인을 조회 목적별 세 쿼리로 분리했습니다.

모든 컬렉션을 한 번에 Fetch Join해 카테시안 곱이 생기는 것도 피했습니다.

그리고 배송지 10곳을 만든 통합 테스트에서 Hibernate의 PrepareStatement 수가 정확히 3회인지 검증해, 데이터가 늘어도 쿼리 수가 증가하지 않도록 회귀 테스트를 만들었습니다.

## 15. 외부 API 실패 격리 - 0:55

배송 계획 저장과 날씨 API 호출을 같은 트랜잭션 안에서 처리하면, 날씨 API 장애 때문에 정상적인 배송 계획까지 롤백될 수 있습니다.

그래서 먼저 계획 저장을 커밋하고, `AFTER_COMMIT` 이벤트에서 날씨와 위험도를 갱신하도록 분리했습니다.

또 배송지를 기상 격자별로 그룹화해 같은 지역의 중복 호출을 줄였습니다. 외부 호출이 일시적으로 실패하면 저장된 위험도를 유지하고, 사용할 데이터가 전혀 없을 때는 억지로 안전하다고 판단하지 않고 `UNKNOWN` 상태로 표현합니다.

핵심 업무와 실패 가능한 외부 시스템 사이에 경계를 둔 것입니다.

## 16. 핵심 기능 요약 - 0:40

추천 기능을 한 번 더 정리하면, 기준은 `위험 등급`, `위험 점수`, `전체 이동시간` 순서입니다.

먼저 안전도를 우선해 후보를 줄이고, 동일하게 안전한 후보들 안에서 상태공간 다익스트라로 전체 순서를 최적화합니다. 그리고 사용자에게 보여줄 첫 구간의 시간은 카카오 길찾기로 보완합니다.

따라서 저희 서비스는 가장 가까운 곳을 추천하는 서비스가 아니라, 안전을 먼저 지키면서 그 안에서 효율을 최적화하는 서비스입니다.

## 17. 테스트와 모니터링 - 0:40

현재 Java 테스트 소스는 41개입니다. 저희는 단순히 결과가 나오는지만 보지 않고, 시스템의 규칙을 테스트하려고 했습니다.

도메인에서는 준비, 배송 중, 완료 상태 전이를 검증했고, 인증에서는 Redis 토큰 회전과 로그아웃, TTL 동작을 검증했습니다. 쿼리는 10곳을 조회해도 3회인지 Hibernate 통계로 확인했습니다.

또 Prometheus와 Grafana를 연결해 애플리케이션 헬스와 JVM, HTTP 지표를 확인할 수 있게 했습니다.

## 18. 배운 점 - 0:40

이번 프로젝트에서 크게 배운 점은 세 가지입니다.

첫째, 인증은 토큰을 만드는 기능이 아니라 발급, 재발급, 회전, 복원과 로그아웃까지 이어지는 생명주기라는 점입니다.

둘째, N+1 해결은 Fetch Join 하나를 추가하는 문제가 아니라 목록과 상세의 조회 목적에 맞게 읽기 모델을 설계하는 문제였습니다.

셋째, 외부 API는 실패할 수 있다는 전제로 핵심 트랜잭션의 경계 밖에 두어야 했습니다.

결국 백엔드 구조와 사용자 화면 모두 사용자가 실제로 내리는 결정 순서에 맞춰야 한다는 것을 배웠습니다.

## 19. 마무리 - 0:20

정리하면 Delivery Insight는 오늘의 물량과 위험을 보고, 안전한 후보를 먼저 판단한 뒤, 효율적인 다음 경로를 추천하는 서비스입니다.

특히 상태공간 다익스트라를 실제 배송 진행 상태와 연결해, 웹 화면에서 바로 다음 행동으로 이어지게 만들었습니다.

## 다익스트라 파트에서 꼭 외울 한 문장

> 일반 다익스트라와 달리 저희 그래프의 정점은 배송지 하나가 아니라, 현재 위치와 이미 방문한 배송지 집합의 조합입니다.

## 발표에서 표현을 조심할 부분

- `Kakao 실제시간`보다는 `카카오 도로 경로 기준 예상 시간`이라고 말한다.
- `다익스트라로 TSP를 완벽하게 해결했다`고 말하지 않고, `TSP와 유사한 순회 문제를 확장된 상태 그래프의 최단경로 문제로 바꿨다`고 설명한다.
- `Redis가 토큰 탈취를 막는다`고 말하지 않고, `로그아웃과 Rotation 이후 탈취 토큰의 재사용을 차단한다`고 설명한다.
- `N+1을 전부 없앴다`고 말하지 않고, `현재 상세 조회 경로에서 배송지 수와 무관하게 세 쿼리로 고정했다`고 설명한다.

## 예상 질문과 짧은 답변

### Q1. 일반 다익스트라를 그대로 쓰면 왜 안 되나요?

현재 위치가 같아도 이미 방문한 배송지 집합에 따라 남은 작업이 달라집니다. 그래서 현재 위치만 정점으로 보면 상태 정보가 부족하고, `(현재 위치, 방문 집합)`을 하나의 정점으로 확장해야 합니다.

### Q2. 이건 다익스트라인가요, TSP인가요?

문제 형태는 출발점이 고정되고 복귀가 없는 TSP와 유사합니다. 구현은 각 방문 상태를 정점으로 만든 확장 그래프에서, 누적 비용이 가장 작은 상태부터 탐색하는 다익스트라 방식입니다.

### Q3. 시간 복잡도가 너무 크지 않나요?

상태 수가 대략 `N x 2^N`으로 증가하기 때문에 전체 배송지를 한꺼번에 넣지 않고, 현재 시점의 미완료 후보를 최대 다섯 곳으로 제한했습니다.

### Q4. 왜 모든 이동시간을 카카오 API로 계산하지 않았나요?

후보 모든 쌍의 비용을 구하려면 호출 수와 응답 지연이 커집니다. 전체 순서 계산은 Haversine 기반 가상 비용으로 빠르게 처리하고, 사용자에게 바로 보여주는 최종 첫 구간만 카카오 예상 시간으로 보완했습니다.

### Q5. 가장 가까운 곳부터 가면 안 되나요?

첫 구간이 가장 짧은 선택이 이후 구간까지 포함한 전체 최적을 보장하지 않습니다. 그래서 각 단계의 가까움이 아니라 모든 후보를 방문하는 누적시간을 비교했습니다.

### Q6. 안전과 이동 효율이 충돌하면 무엇을 우선하나요?

안전을 우선합니다. 위험 등급과 위험 점수가 가장 낮은 후보군을 먼저 고른 뒤, 그 후보들 안에서만 이동시간을 최적화합니다.

### Q7. 위험 데이터가 없으면 어떻게 하나요?

데이터가 없거나 유효하지 않으면 `UNKNOWN`으로 두고, 안전하다고 간주하지 않도록 가장 낮은 우선순위로 처리합니다.

### Q8. 왜 A*나 다른 휴리스틱을 쓰지 않았나요?

후보가 최대 다섯 곳이라 상태공간이 제한적이고, 정확한 최소 누적비용을 확인하는 것이 목적이어서 구현과 검증이 명확한 다익스트라 방식을 선택했습니다.
